2. Deep-Dive: Docker, Redis, Kafka, Idempotency & Roles

🐳 1. Docker & Container Orchestration

Where it is used: Full local dev stack (docker-compose.yml) and multi-stage production deployment (docker-compose.prod.yml).

How they are connected:

  • PostgreSQL 16: Port 5432 with health check (pg_isready). Stores all ACID entities.
  • Redis 7: Port 6379 with health check (redis-cli ping). Acts as lock coordinator and cache.
  • Zookeeper & Kafka: Port 2181 & 9092. Orchestrates partitions and consumer offset synchronization.
  • Spring Boot Backend: Multi-stage build (maven:3.9.6-eclipse-temurin-21-alpine ➔ eclipse-temurin:21-jre-alpine). Runs under an unprivileged user railflow.
  • React Frontend: Multi-stage build (node:20-alpine ➔ nginx:1.25-alpine). Reverse-proxies /api/ to backend:8080.

⚡ 2. Redis & Redisson Concurrency Engine

Where it is used: SeatInventoryService.java, IdempotencyService.java, and route caching.

How it works:

  • Distributed Locking (RLock): When thousands hit Tatkal at once, Redisson acquires a fair lock on key lock:inventory:{trainId}:{journeyDate}:{coachType} in Redis memory.
  • Seat Hold Sliding TTL: When a user holds a berth, a temporary hold key is set in Redis with 10-minute TTL (expires_at = now() + 10m). If the user abandons checkout, the hold naturally expires and is reclaimed.
  • Idempotency L1 Cache: Caches responses for key idempotency:{key} with 24-hour TTL for instant sub-millisecond duplicate interception.

📨 3. Apache Kafka & Transactional Outbox

Where it is used: Asynchronous event messaging between Booking, Payment, Notification, and Waiting List services.

How they are connected & data flows:

  • Transactional Outbox: Instead of making network calls during payment/booking, Spring Boot inserts an event into PostgreSQL table outbox_events within the same ACID transaction.
  • Outbox Publisher Job: OutboxPublisherJob.java runs every 5 seconds, reads PENDING events, publishes to Kafka topics, and marks them PUBLISHED.
  • Kafka Topics:
    • booking-confirmed-events: Consumed by BookingEventConsumer to generate binary PDF tickets via OpenPDF and send confirmation emails.
    • booking-cancelled-events: Consumed to trigger passenger refund ledgers and auto-promote waitlisted passengers.
  • Consumer Groups: railflow-notification-group handles load balancing and partition reassignment across nodes.

🔑 4. Idempotency & Role-Based Access Control (RBAC)

Idempotency Engine (IdempotencyService.java):

  • Frontend transmits header Idempotency-Key: idem_uuid on every write request.
  • Backend checks Redis L1 cache first; if absent, checks PostgreSQL idempotency_records table.
  • If key is COMPLETED, returns cached response immediately. If PROCESSING, rejects concurrent duplicate (409 Conflict). If new, registers key and executes request.

Roles & RBAC Architecture:

  • Table roles stores ROLE_USER and ROLE_ADMIN. Table user_roles maps user IDs.
  • Spring Security intercepts every request in JwtAuthenticationFilter, extracts claims, and populates SecurityContext.
  • Protected endpoints use method-level security: @PreAuthorize("hasRole('ADMIN')") on AdminController and train fleet creation.

5. End-to-End Operational Data Flow

1
Train Search: Client queries GET /api/v1/trains/search?from=NDLS&to=BSB&date=2026-11-25.
Backend checks route stations, running days, queries seat_inventory, and returns live fares and coach availability.
2
Coach Seat Selection: Passenger opens CoachSeatPicker.jsx, selects Coach C1 Seat 15 (Window).
Passenger details are attached with chosenCoach and chosenSeatNumber.
3
Seat Hold & Distributed Lock: Client submits POST /api/v1/bookings with header Idempotency-Key.
Backend acquires Redisson lock: lock:inventory:2:2026-11-25:CC.
Decrements inventory, creates 10-minute SeatHold in PostgreSQL + Redis, creates Booking (PAYMENT_PENDING, PNR generated), and releases lock.
4
Payment & Webhook Verification: Client calls POST /api/v1/payments/create-order then /payments/verify.
Backend verifies HMAC-SHA256 signature, transitions payment to SUCCESS, confirms booking in PostgreSQL, and inserts event into outbox_events.
5
Kafka Streaming & PDF Dispatch: OutboxPublisherJob polls pending events and publishes to Kafka booking-confirmed-events.
BookingEventConsumer receives event, generates binary PDF ticket via OpenPDF + ZXing QR, and sends email notification.
6
Cancellation & WL Auto-Promotion: When a confirmed booking is cancelled:
Backend calculates cancellation fee (IRCTC rules), updates status to CANCELLED, and calls WaitingListService.
Eligible passengers in waiting_lists are promoted (WL ➔ RAC ➔ CONFIRMED), claiming vacated berths automatically!

6. Comprehensive Technical Viva Voce Q&A Master List

Q1: How does RailFlow prevent the double-booking problem during high-concurrency Tatkal rush?
Answer: RailFlow avoids database row lock bottlenecks by using Redisson Distributed Locks (RLock) on Redis. Before inventory is decremented, the thread acquires a fair lock on key lock:inventory:{trainId}:{date}:{coachType} with a 3-second wait time and 5-second lease time. Only the lock holder modifies inventory, holds the seat with a 10-minute TTL, and immediately releases the lock, serializing requests at memory speed without database deadlocks.
Q2: What is the Transactional Outbox Pattern and why is it used with Kafka?
Answer: The Transactional Outbox pattern solves the dual-write problem (writing to a database and publishing to Kafka simultaneously). Instead of directly calling Kafka during a user request (which could fail if Kafka is down while the DB commit succeeded), Spring Boot saves the event into the outbox_events table within the same database transaction. A background scheduler (OutboxPublisherJob) polls pending events and streams them to Kafka, ensuring guaranteed At-Least-Once Delivery.
Q3: How does the Idempotency mechanism prevent duplicate bookings and payments?
Answer: The client generates a unique UUID (Idempotency-Key) and passes it in the request header. IdempotencyService checks Redis cache first (24h TTL) and falls back to PostgreSQL idempotency_records. If the key exists with status COMPLETED, it returns the cached response immediately without re-executing booking logic. If a request with the same key is currently PROCESSING, it blocks duplicate execution, preventing double-charges on rapid double-clicks.
Q4: How does RailFlow manage Role-Based Access Control (RBAC) securely?
Answer: RailFlow stores roles in a separate roles table (ROLE_USER, ROLE_ADMIN) joined via user_roles. When a user authenticates, JwtTokenProvider encodes the granted authorities into the JWT claims payload. For every request, JwtAuthenticationFilter validates the token and populates Spring's SecurityContext. Controllers enforce access using @PreAuthorize("hasRole('ADMIN')"), while the frontend dynamically gates administrative views based on the decoded token.
Q5: How does the Automated Waiting List (WL) Promotion Engine work?
Answer: In CancellationService.java, whenever a confirmed ticket is cancelled, the service invokes WaitingListService.promoteEligiblePassengers() with the number of released berths. It queries the waiting_lists FIFO queue ordered by position, promotes RAC passengers to CONFIRMED, promotes WAITING_LIST passengers to RAC or CONFIRMED, updates their passenger status, and emits a Kafka notification event.
Q6: How does RailFlow's multi-stage Docker deployment optimize performance and security?
Answer:
  • Backend: Stage 1 uses full Maven to compile the jar; Stage 2 copies only the final jar to a minimal eclipse-temurin:21-jre-alpine image (180MB) and executes under an unprivileged user railflow with container memory limits (-XX:MaxRAMPercentage=75.0).
  • Frontend: Stage 1 uses Node 20 to generate optimized Vite bundles; Stage 2 serves the assets via Nginx Alpine with Gzip compression, client-side routing fallback (try_files $uri /index.html;), and reverse-proxies /api/ to the Spring Boot backend.
